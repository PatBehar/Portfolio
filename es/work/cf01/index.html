Procesamiento y calificación de leads

De un proceso manual a un flujo comercial trazable e integrado con un CRM simulado.

01 / CONTEXTO DE NEGOCIO

Una ruta más clara desde la recepción del lead hasta el CRM

Atlas Services · escenario ficticio

Las consultas llegan mediante formularios web y procesos basados en CSV. En este flujo hipotético, el equipo valida datos de contacto, interpreta la intención, asigna prioridad e ingresa los registros manualmente en un CRM.

Escenario diseñado · no es un cliente ni una operación observada.

  • Validación inconsistente

    Los datos requeridos y la asignación pueden variar entre traspasos.

  • Registros duplicados

    El ingreso manual repetido crea riesgo de duplicados en el CRM.

  • Excepciones poco visibles

    Los fallos de integración necesitan una ruta visible y recuperable.

02 / DISEÑO DEL PROCESO

Diseño de proceso y arquitectura

AS-IS es una línea base manual hipotética; TO-BE es un flujo propuesto basado en reglas. El diagrama de arquitectura se identifica expresamente como una propuesta, no como el sistema en ejecución. El dashboard local y el código fuente son evidencias separadas de implementación.

03 / IMPLEMENTACIÓN LOCAL

Una ruta controlada desde la recepción hasta el CRM

El prototipo local usa FastAPI y Pydantic para recibir leads estructurados y aplica reglas explícitas antes de escribir en el CRM.

  1. 01

    Recibir y validar

    Aceptar JSON estructurado y revisar los datos de negocio requeridos.

  2. 02

    Asignar y calificar

    Aplicar reglas determinísticas para ventas/soporte; los casos inválidos o ambiguos pasan a revisión humana.

  3. 03

    Escribir con controles

    Llamar a un Mock CRM local separado mediante HTTP real REST/JSON.

  4. 04

    Persistir y recuperar

    Conservar registros SQLite separados, trazas y auditoría; los fallos siguen siendo recuperables.

Controles de confiabilidad

  • Mismo ID y mismo contenido → repetición idempotente; no se escribe otra vez en el CRM.
  • Mismo ID con contenido distinto → HTTP 409; no se sobrescribe el registro original.
  • Caída del CRM → estado pendiente/recuperable y luego reintento manual explícito.

Dos servicios Docker Compose · solo la app se vincula a localhost; el Mock CRM permanece en la red privada.

04 / CALIFICACIÓN COMERCIAL

Calificación comercial transparente basada en reglas

Solo se califican leads válidos de ventas que incluyen explícitamente los tres datos requeridos. Ejemplos:

HOT100 / 100

75–100

Inmediato · presupuesto confirmado · necesidad alta

Priorizar contacto
WARM65 / 100

45–74

Dentro de 30 días · presupuesto desconocido · ajuste parcial

Programar seguimiento
COLD30 / 100

0–44

Explorando · presupuesto no compatible · necesidad poco clara

Nutrir / reevaluar ajuste

NOT_SCORED · si faltan datos de calificación, no se clasifica como COLD.

NOT_APPLICABLE · las solicitudes de soporte quedan fuera de la calificación de ventas.

Puntajes ilustrativos con datos sintéticos · no son probabilidades de conversión, SLA ni una política productiva de prioridad comercial.

05 / DECISIÓN TÉCNICA

Reglas cuando los datos son conocidos

Los campos estructurados y criterios explícitos permiten explicar y probar la validación determinística. Los datos inválidos y las intenciones ambiguas quedan para una persona, sin que un modelo tenga que adivinarlos.

“ai_candidate” es solo una etiqueta para revisión. El sistema no hace llamadas LLM; se utilizaron herramientas asistidas por IA durante el desarrollo.

Stack del prototipo

  • Python 3.12
  • FastAPI
  • Pydantic
  • REST / JSON
  • SQLite ×2
  • Docker Compose
  • pytest
  • HTML / CSS / JavaScript vanilla

Evidencia y validación de la implementación

Límites del prototipo

  • Escenario ficticio de Atlas Services con leads y puntajes sintéticos; Mock CRM, no integración con proveedor.
  • Demo solo local; sin autenticación/TLS de producción, importación CSV real, reintentos en segundo plano ni LLM.
  • Sin evidencia de clientes, conversiones, ROI, ahorro o impacto operativo real.
