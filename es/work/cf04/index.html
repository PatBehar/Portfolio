01 / CONTEXTO DE NEGOCIO

Hacer visible y recuperable el trabajo entre sistemas

Northstar Services · organización de servicios ficticia

Northstar Services es una organización ficticia y sus eventos de soporte son sintéticos. Cuando se abre un caso, Operaciones necesita actualizar de forma coordinada el registro del CRM y la cola de tickets. Si un sistema guarda el cambio y el otro falla —o se pierde una confirmación—, el equipo debe averiguar qué ocurrió antes de reintentar. Este prototipo hace visible la ejecución parcial y muestra una recuperación limitada sin escrituras duplicadas.

Flujo ficticio con eventos sintéticos y servicios locales Mock CRM y Mock Ticketing independientes.

  • Ejecución parcial

    Un destino puede guardar cambios mientras otro está temporalmente indisponible.

  • Escrituras duplicadas

    Una repetición no debe crear otro registro de CRM o ticket.

  • Recuperación poco clara

    Los reintentos deben tener límites y una ruta manual visible.

02 / DISEÑO DEL PROCESO

Diagramas originales de proceso y arquitectura

Las exportaciones muestran el traspaso manual, la orquestación propuesta y los límites entre servicios locales. La demo usa tres procesos locales independientes por HTTP/JSON.

03 / FLUJO IMPLEMENTADO

Tres servicios coordinan solicitudes HTTP locales reales

El orquestador local valida eventos sintéticos y se comunica por HTTP/JSON con servicios Mock CRM y Mock Ticketing separados; cada uno mantiene su propio almacén SQLite.

  1. 01

    Enviar un evento

    Validar el contenido y la huella del evento; luego crear o localizar el registro de orquestación.

  2. 02

    Escribir en CRM

    Aplicar la clave idempotente y mantener un único registro CRM sintético.

  3. 03

    Entregar al sistema de tickets

    Crear un ticket sintético o mostrar un fallo recuperable con reintentos limitados.

  4. 04

    Recuperar y auditar

    Reintentar o reproducir desde el estado visible y registrar intentos y outbox local.

Consistencia y límites

  • Los eventos duplicados exactos devuelven el resultado existente; el contenido distinto bajo la misma identidad genera conflicto.
  • La recuperación de una confirmación perdida evita duplicar una escritura ya confirmada.
  • El outbox de notificaciones es local; su entrega es simulada y no envía mensajes.

Tres servicios HTTP locales independientes y sus propias bases SQLite · sin notificaciones ni sistemas de clientes externos.

04 / DECISIÓN TÉCNICA

Límites explícitos entre servicios y estado recuperable

El orquestador local administra la identidad, los intentos y la recuperación; cada servicio de destino administra su propia persistencia. La ejecución parcial queda visible y la repetición es explícita.

CRM y tickets son simulaciones locales; el outbox de notificaciones no envía correos ni mensajes.

Stack del prototipo

  • Python 3.12
  • FastAPI ×3 servicios
  • HTTP / JSON
  • Almacenes SQLite ×3
  • Huella idempotente
  • Outbox persistente
  • HTML / CSS / JavaScript local
