01 / BUSINESS CONTEXT

Make cross-system work observable and recoverable

Customer support operations · fictional scenario

A support event needs coordinated updates in a customer record and a ticketing queue. Partial failures and lost acknowledgments should be visible without creating duplicate writes.

Fictional workflow using synthetic events and independent local Mock CRM and Mock Ticketing services.

  • Partial completion

    One destination may commit while another is temporarily unavailable.

  • Duplicate writes

    A repeated request must not create another CRM or ticket record.

  • Unclear recovery

    Retries need bounded attempts and a visible manual path.

02 / PROCESS DESIGN

Original process and architecture diagrams

These source exports show the manual handoff, the proposed orchestrated flow and the local service boundaries. The running demo uses three local processes over HTTP/JSON.

03 / IMPLEMENTED FLOW

Three services coordinate real local HTTP requests

The local orchestrator validates synthetic events and sends them over HTTP/JSON to separate Mock CRM and Mock Ticketing services, each with its own SQLite store.

  1. 01

    Submit an event

    Validate payload and event fingerprint, then create or locate the orchestration record.

  2. 02

    Write to CRM

    Apply the idempotency key and preserve the unique CRM record.

  3. 03

    Deliver to ticketing

    Create the synthetic ticket or surface a bounded retryable failure.

  4. 04

    Recover & audit

    Retry or replay from the visible state; track attempts and local outbox events.

Consistency and limits

  • Exact duplicate events return the existing result; changed content under the same identity conflicts.
  • Lost acknowledgment is recovered without duplicating the already-committed write.
  • Notification outbox records are local; delivery is simulated and sends no message.

Three separate local HTTP services with separate SQLite stores · no external notifications or customer systems.

04 / TECHNICAL CHOICE

Explicit service boundaries with recoverable state

A local orchestrator owns identity, attempts and recovery while each downstream service owns its own persistence. Partial completion remains observable and replay is explicit.

The CRM and ticketing systems are local mocks; the notification outbox does not send email or messages.

Prototype stack

  • Python 3.12
  • FastAPI services ×3
  • HTTP / JSON
  • SQLite stores ×3
  • Idempotency fingerprints
  • Persistent outbox
  • Local HTML / CSS / JavaScript
